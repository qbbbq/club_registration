# 后台学生信息与报名修改设计

日期：2026-09-05  
状态：已确认，待编写实现计划

## 目标

在后台新增“修改信息”Tab。管理员输入学生身份证号后，可以查看学生资料和当前报名信息，并在一个操作中修改学生个人信息、修改报名社团或为没有报名记录的学生补录报名。

## 已确认的规则

- 使用 B 双栏工作台布局。
- 可编辑个人信息包括：姓名、身份证号、年级、班级。
- 年级只能是“初一”“初二”“初三”，且保存时必填。
- 已有报名记录更换社团时，原社团剩余名额加 1，目标社团剩余名额减 1。
- 更换社团保留原报名记录 ID 和报名时间。
- 没有报名记录时，管理员可以选择社团补录报名，也可以只保存学生资料。
- 不支持把已有报名改成“无报名”。
- 目标社团已满、年级不匹配、身份证号重复或其他校验失败时，整次保存回滚。
- 不新增数据库表，不修改 `registrations` 表结构。
- 身份证号末位 `x` 统一规范为大写 `X` 后再保存和计算哈希；部署时执行迁移脚本同步历史报名哈希。

## 现有数据结构

`students` 表保存 `id`、`name`、`id_card`、`grade`、`class_name`。`id_card` 唯一，`grade` 可空以兼容历史数据。

`registrations` 表保存 `id`、`name`、`id_card_hash`、`class_name`、`club_id`、`created_at`。身份证原文不存储，`id_card_hash` 为 SHA-256，并且唯一。

`clubs` 表保存 `grade`、`total_quota` 和 `remaining_quota`。社团年级为空的历史记录不能作为新报名目标。

## 后端设计

### 查询接口

新增：

```text
POST /api/admin/student-registration/lookup
```

请求体：

```json
{ "idCard": "身份证号" }
```

处理规则：

- 校验身份证号为 18 位格式。
- 按身份证号查询学生。
- 使用当前身份证号计算 SHA-256，再查询对应报名记录，并关联社团名称。
- 学生不存在时返回失败信息。
- 学生存在但没有报名时，返回 `registration: null`。

成功返回的数据包含：

```json
{
  "student": {
    "id": 1,
    "name": "张三",
    "idCard": "身份证号",
    "grade": "初一",
    "className": "初一(1)班"
  },
  "registration": {
    "id": 10,
    "clubId": 2,
    "clubName": "篮球社",
    "time": "报名时间"
  }
}
```

### 保存接口

新增：

```text
PUT /api/admin/student-registration/:studentId
```

请求体：

```json
{
  "idCard": "身份证号",
  "name": "张三",
  "grade": "初一",
  "className": "初一(1)班",
  "clubId": 2
}
```

`clubId` 在学生没有报名且只想修改个人资料时可以为空；已有报名记录时必须保留当前社团或选择其他社团。

保存必须通过一个 MySQL 事务完成：

1. 按 `studentId` 锁定学生，确认记录存在。
2. 校验姓名、班级、身份证号和固定年级；新身份证号不能被其他学生占用。后台编辑与公共报名都先锁定学生，再锁定报名记录，最后按社团 ID 升序锁定社团。
3. 根据旧身份证号哈希查找并锁定当前报名记录。
4. 锁定当前社团和目标社团，按固定顺序获取锁以减少并发死锁风险。
5. 校验目标社团存在、年级等于修改后的学生年级，并且有剩余名额；如果目标社团就是当前社团，则允许保留该社团，即使其剩余名额为 0。历史年级为空的当前社团可以被原样保留，不作为新的报名目标；如果切换到它则拒绝。
6. 更新 `students` 的姓名、身份证号、年级和班级。
7. 有报名记录时更新报名记录的姓名、班级、身份证哈希和 `club_id`；更换社团时调整原社团和目标社团的剩余名额。
8. 没有报名记录且选择了目标社团时新增报名记录并扣减目标社团名额。
9. 提交事务后清除社团列表缓存，返回更新后的学生和报名信息。

同一社团修改个人资料时不调整名额。身份证号变化时，报名记录的 `id_card_hash` 必须同步变化。任何步骤失败都回滚学生资料、报名记录和社团名额。

公共 `POST /api/register` 报名流程不改变；后台修改接口不能绕过社团年级、名额和身份证唯一性校验。

## 前端设计

在 `Admin.vue` 的 `el-tabs` 中新增：

```text
label="修改信息" name="student-registration"
```

Tab 内容采用双栏工作台：

- 顶部：身份证号输入框、查询按钮、清空按钮。
- 左栏：学生信息编辑表单，字段为姓名、身份证号、年级下拉框、班级。
- 右栏：当前报名信息、报名时间和目标社团下拉框。
- 社团选项显示社团名称、年级和剩余名额；按照正在编辑的学生年级过滤，满员社团不可选，但当前已报名社团即使剩余名额为 0 也必须保持可选，以便只修改个人资料。
- 没有报名记录时显示“暂无报名”，目标社团为空时允许只保存学生资料。
- 已有报名记录时目标社团默认当前社团，不提供空选项。
- 保存按钮提交全部字段，保存期间禁用表单，避免重复提交。
- 保存成功后重新查询当前学生，并刷新学生、报名和社团列表。
- 查询失败或保存失败时保留已显示的编辑内容，并展示服务端返回的错误信息。
- 双栏在窄屏下改为上下排列。

查询身份证号变化后清空当前结果，避免把上一名学生的报名记录误保存到新查询中。保存成功并修改了身份证号后，查询框同步为新身份证号。

## 错误处理

- 身份证号为空或格式错误：返回 HTTP 400。
- 学生不存在：返回 HTTP 404 和现有接口风格的失败响应体，前端显示明确提示。
- 年级为空或非法：返回 HTTP 400。
- 新身份证号已被其他学生或报名记录使用：返回失败，不修改任何数据。
- 目标社团不存在、未设置年级、年级不匹配或切换目标社团时名额已满：返回失败，不修改任何数据；保留当前已报名社团时不受其剩余名额为 0 的影响。历史当前社团年级为空时，只允许保留，不允许作为新目标切换进入。
- 数据库异常：事务回滚，返回 HTTP 500；前端保留表单内容，允许重试。

## 测试设计

### 后端路由测试

- 合法身份证号能查询学生及当前报名。
- 学生存在但没有报名时返回空报名。
- 学生不存在和身份证号格式错误时返回失败。
- 保存四项个人信息。
- 新身份证号能同步更新报名哈希。
- 更换社团时保留报名 ID 和时间，并正确调整两个社团名额。
- 无报名学生补录社团并扣减名额。
- 无报名学生只修改个人资料。
- 重复身份证号、非法年级、社团不存在、年级不匹配和社团已满均被拒绝。
- 任一失败场景都不产生部分更新。
- 身份证号末位大小写 `x/X` 视为同一个学生，历史哈希迁移后不能形成第二条报名。
- 后台修改与公共报名并发时保持一致的学生、报名、社团锁顺序。
