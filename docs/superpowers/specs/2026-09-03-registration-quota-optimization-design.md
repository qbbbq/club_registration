# 报名事务名额扣减与快速满额拒绝设计

日期：2026-09-03  
状态：设计已确认，待实施计划

## 背景

线上 1000 人同时选择同一社团的测试中，名额一致性正确：66 个名额只成功 66 人，没有超卖。但当前报名流程在 `RegistrationService.register` 中使用 `SELECT ... FOR UPDATE` 读取社团行，同一社团的并发请求会在同一行上排队；名额耗尽后的请求也需要先获得行锁才能返回“名额已满”。

本次优化只针对报名事务的名额扣减和满额快速拒绝。已确认保持同步报名接口，不引入 Redis 或其他新基础设施。

## 已确认的约束

- `POST /api/register` 继续同步返回。
- 成功、名额已满、重复报名等现有消息保持不变。
- 不修改前端交互和 API 响应结构。
- 只修改现有 Node + MySQL 实现，不新增 Redis、消息队列或其他数据库中间件。
- 不新增数据库表或迁移；继续使用现有 `clubs` 主键和 `registrations.id_card_hash` 唯一索引。
- 保留请求取消、事务回滚和未知数据库错误的现有处理方式。
- 开放时间格式问题不属于本次优化范围。

## 目标与非目标

### 目标

1. 名额扣减使用数据库原子条件更新，保证并发下不会扣成负数。
2. 已经确认名额为 0 的请求不进入事务，直接返回“该社团名额已满”。
3. 竞态条件下原子更新失败的请求返回相同的满额消息。
4. 重复报名或其他写入异常不会造成名额泄漏。
5. 保持现有接口和前端兼容性。

### 非目标

- 不实现异步报名队列或返回 HTTP 202。
- 不实现跨 PM2 进程的全局队列。
- 不在本次改动中引入 Redis、CDN 或 CC/WAF。
- 不改变报名开放时间功能。

## 方案

采用“普通预检查 + 条件原子扣减 + 事务回滚”的方案。

### 请求流程

```text
POST /api/register
  ↓
路由校验请求格式和学生身份
  ↓
读取开放时间（保持现有判断和消息）
  ↓
普通查询社团（不加锁）
  ├─ 不存在 → 返回“社团不存在”
  └─ remaining_quota <= 0 → 立即返回“该社团名额已满”
  ↓
开启 MySQL 事务
  ↓
条件原子扣减名额
  ├─ affectedRows = 0 → 返回“该社团名额已满”
  └─ affectedRows = 1
       ↓
    插入报名记录
       ├─ ER_DUP_ENTRY → 抛出内部重复异常，事务回滚
       └─ 其他异常 → 事务回滚并向上抛出
       ↓
    读取创建时间并提交
       ↓
    返回现有成功响应
```

### 普通预检查

使用社团主键查询，不使用 `FOR UPDATE`：

```sql
SELECT id, name, total_quota, remaining_quota
FROM clubs
WHERE id = ?
LIMIT 1
```

这一步只负责快速路径和错误消息，不负责并发正确性。预检查结果可能在事务开始前变旧，因此后续必须再次依赖原子更新判断。

### 原子扣减

事务内执行：

```sql
UPDATE clubs
SET remaining_quota = remaining_quota - 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = ?
  AND remaining_quota > 0
```

- `affectedRows = 1` 表示本事务拿到一个名额。
- `affectedRows = 0` 表示名额已经耗尽或在竞态中被其他请求拿走，返回“该社团名额已满”。
- 条件更新是最终并发判定，不能改为先读后写。
- 事务内不再执行 `SELECT ... FOR UPDATE` 读取社团行。

### 报名插入与回滚

原子扣减成功后插入 `registrations`。如果 `id_card_hash` 唯一索引触发 `ER_DUP_ENTRY`，抛出内部重复异常，让 `withTransaction` 回滚本次名额扣减，事务外转换为现有重复报名消息。

这样不需要手工执行“名额加回”补偿 SQL，避免补偿失败或并发交错造成计数错误。其他数据库异常同样通过事务回滚恢复名额。

## 组件改动

### `server/src/services/registrationService.ts`

- 将开放时间检查放在事务创建之前，保留现有判断逻辑和返回消息。
- 增加不加锁的社团预查询。
- 移除报名流程中的 `SELECT ... FOR UPDATE`。
- 使用条件原子 `UPDATE` 检查名额。
- 增加内部重复异常类型或等价哨兵错误，用于在事务外映射重复报名响应。
- 成功响应继续使用预查询得到的社团名称和现有创建时间字段。

### 其他模块

- `server/src/routes/register.ts`：不改请求字段、响应字段或路由行为。
- `server/src/storage/database/mysql-client.ts`：不改连接池和事务接口。
- 数据库 schema：不改表结构、不执行迁移。
- 前端：不改动。

## 错误行为

| 情况 | HTTP | 响应消息 | 名额结果 |
| --- | ---: | --- | --- |
| 预检查发现已满 | 200 | 该社团名额已满 | 不变 |
| 原子扣减 `affectedRows = 0` | 200 | 该社团名额已满 | 不变 |
| 原子扣减成功并插入成功 | 200 | 报名成功 | 减少 1 |
| 唯一索引重复 | 200 | 该身份证号已报名过社团 | 事务回滚，不变 |
| 其他数据库异常 | 500 | 现有服务器错误消息 | 事务回滚 |
| 请求取消或超时 | 不返回新响应 | 沿用现有中止处理 | 事务回滚 |

## 并发正确性

- 多个请求竞争同一社团时，每个请求只能通过一次条件原子更新，成功数不会超过初始 `remaining_quota`。
- 名额耗尽后，新请求通过普通预检查快速结束；已经通过预检查的请求会在条件更新处再次被拦截。
- 同一身份证号并发报名时，唯一索引只允许一个插入成功；其他事务回滚已扣除的名额。
- 同一学生并发选择不同社团时，唯一索引仍保证最多一条报名记录，失败事务恢复对应社团名额。
- 社团不存在的正常路径由预检查识别；极少见的删除竞态会由原子更新失败进入满额响应路径，不影响名额安全性。

## 测试设计

调整 `server/src/services/registrationService.test.ts`，覆盖：

1. 预检查发现名额为 0，不创建事务，返回满额消息。
2. 预检查有名额，但原子更新返回 `affectedRows = 0`，不执行插入，返回满额消息。
3. 原子更新成功后插入成功，返回成功且执行创建时间查询。
4. 插入触发 `ER_DUP_ENTRY`，事务回调抛出内部重复异常并由 service 转换为重复报名消息。
5. 插入或创建时间查询抛出未知错误，错误继续抛出，依赖 `withTransaction` 回滚。
6. 开放时间未到、社团不存在、请求取消等现有行为保持不变。
7. 验证报名 SQL 不再包含 `FOR UPDATE` 社团读取语句。

验收命令：

```text
corepack pnpm test
corepack pnpm run build:server
corepack pnpm run build
```

部署后使用固定 Keep-Alive 连接池进行对照压力测试，检查：

- 目标社团成功数不超过总名额。
- `remaining_quota >= 0`。
- 报名记录数与名额扣减一致。
- 重复报名不消耗名额。
- 满额后的请求不产生 5xx。
- P95、P99 和超时数量相较当前基线下降。

## 部署与回滚

- 无数据库迁移，部署内容只有编译后的 Node 后端代码。
- 发布前运行全部测试和前后端构建。
- 发布后先执行少量成功报名、重复报名和满额检查，再执行受控压力测试。
- 如出现异常，回滚到上一版 `dist-server` 即可，不需要回滚数据库结构。
- 线上已有报名记录不得使用“清空全部报名”方式处理；压力测试必须使用可识别、可单独清理的数据集或隔离环境。

## 后续可选方向

如果原子扣减优化后仍无法满足真实高峰需求，再单独评估跨 PM2 进程共享的名额令牌或排队机制。本次不提前引入，以避免把同步报名改成异步流程并扩大故障面。
