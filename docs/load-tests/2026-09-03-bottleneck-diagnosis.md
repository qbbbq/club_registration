# 1000 人并发报名结果诊断

## 结论

上一轮 1000 人同一社团测试暴露了真实问题，但 21 秒尾延迟和 53 个超时不能全部归因于 MySQL 报名事务。测试同时制造了 1000 条新的 HTTPS/TLS 连接，连接建立风暴本身已经足以拖慢入口层。

当前系统的名额一致性是正确的：66 个名额只成功 66 人，没有超卖。但高峰期体验仍不理想，应该分别优化压测方法、入口连接层和同一社团的报名事务。

## 已获得的证据

### 1000 条新连接的全并发对照

| 接口 | 结果 | P50 | P95 | P99 |
| --- | --- | ---: | ---: | ---: |
| `GET /health`，不访问 MySQL | 553 个 200，447 个客户端超时 | 9842 ms | 21310 ms | 21331 ms |
| `GET /api/clubs`，缓存读取 | 762 个 200，238 个客户端超时 | 3560 ms | 21182 ms | 21200 ms |
| `POST /api/students/lookup`，MySQL 只读 | 1000 个 200 | 3582 ms | 10122 ms | 10317 ms |

健康检查也出现大量超时，说明 1000 条新 TLS 连接会显著放大客户端、Nginx 或入口连接层的压力。

### 200 条 Keep-Alive 连接的对照

总请求数仍为 1000，仅将客户端连接窗口限制为 200，避免一次建立 1000 条新 TLS 连接。

| 接口 | 结果 | P50 | P95 | P99 |
| --- | --- | ---: | ---: | ---: |
| `GET /health` | 999 个 200，1 个客户端超时 | 97 ms | 410 ms | 442 ms |
| `GET /api/clubs` | 1000 个 200 | 356 ms | 866 ms | 1132 ms |
| `POST /api/students/lookup` | 1000 个 200 | 113 ms | 170 ms | 182 ms |

这说明入口层和压测客户端的连接建立方式是重要变量，不能用单机 1000 条新连接的结果直接代表 1000 个真实浏览器用户的服务端处理能力。

### 同一社团真实报名测试

目标社团为「男子篮球社」，编号 39，名额 66。1000 个请求全部指向该社团：

| 结果 | 数量 |
| --- | ---: |
| 业务成功 | 66 |
| 业务返回“名额已满” | 881 |
| 客户端连接超时 | 53 |
| HTTP 5xx | 0 |

测试后名额为 `0/66`，未超卖；测试数据随后已清理。由于这组请求也同时建立了大量新 HTTPS 连接，所以其中的 53 个超时包含入口连接压力，不能单独作为数据库行锁的量化结果。

## 代码层面的已知热点

- `server/src/services/registrationService.ts` 在报名事务中对目标社团执行 `SELECT ... FOR UPDATE`。同一社团的 1000 个请求会竞争同一行，这是正确性和尾延迟之间的主要冲突点。
- `server/index.ts` 的并发限制是每个 PM2 进程独立生效的。4 个 PM2 进程并不是一个全局队列，同一社团的请求可能分散到多个进程后再一起竞争 MySQL。
- Nginx 配置当前只声明了 `listen 443 ssl`，尚未明确启用 HTTP/2；这会让真实浏览器和单机压测的连接行为更依赖入口层连接数。
- 开放时间接口目前返回 `2026-09-03T016:03:00+08:00`，小时字段多了一个 `0`，不是合法 ISO 时间。这个问题与性能无关，但会使后端跳过有效的时间门禁判断。

## 建议的优化顺序

1. 修正开放时间格式，避免无效配置绕过时间门禁。
2. 把压测器改成固定连接池或多进程、多来源压测，并分别记录连接建立、服务端等待和完整响应时间。
3. 优化报名事务：使用带 `remaining_quota > 0` 条件的原子扣减，缩短同一社团的锁持有时间，并对已满状态做快速拒绝。
4. 如果确实存在报名瞬时洪峰，再引入跨 PM2 进程共享的排队或名额令牌机制；单进程内存队列无法形成全局背压。
5. 静态页面可以使用 CDN，API 不应直接交给 CDN 缓存；CC/WAF 主要用于限制恶意流量，不能替代报名事务优化。

## 数据安全说明

诊断期间没有执行写入型对照测试。发现的 6 条线上报名记录来自其他社团和其他学生，属于真实线上数据，未执行全表清理。
